## 微服务架构设计
微服务是什么->拆分原则->拆分维度->服务间通信->数据管理->DDD简介->面试高频题
### 微服务是什么
微服务：把单体应用拆分成多个独立部署的小服务，每个服务独立开发、部署、扩展。
```
单体架构：一个应用包含所有功能（订单+库存+用户）
    ↓ 拆分
微服务：
┌─────────┐ ┌─────────┐ ┌─────────┐
│ 订单服务 │ │ 库存服务 │ │ 用户服务 │
│ (独立部署)│ │ (独立部署)│ │ (独立部署)│
└─────────┘ └─────────┘ └─────────┘
```
单体 vs 微服务

|对比|单体|微服务|
|---|---|---|
|**部署**|一个包|多个独立|
|**扩展**|整体扩展|按需扩展|
|**技术栈**|统一|可异构|
|**故障影响**|全部|局部|
|**复杂度**|低|高（分布式）|
### 拆分原则
高内聚、低耦合
```
// 高内聚：一个服务内功能紧密相关
// 低耦合：服务间依赖少

// 例子：
// 订单服务的功能：创建订单、查询订单、订单状态
// 不要：订单服务里混入用户管理功能
```
拆分判断标准
```
// ① 业务边界清晰（是否属于同一业务域）
// ② 独立变化（不同步变更的功能拆开）
// ③ 独立扩展（不同扩展需求拆开）
// ④ 故障隔离（重要和次要功能分开）
// ⑤ 团队组织（康威定律：组织结构决定系统结构）
```
什么时候不该拆
```
// ① 团队小、业务简单 → 单体（避免过度设计）
// ② 强事务关联 → 先合并（分布式事务难）
// ③ 数据强一致 → 谨慎拆（跨库事务）
// ④ 没有独立扩展需求 → 不拆
// ⑤ 团队协作成本 > 拆分收益 → 不拆
```
### 拆分维度
按业务能力拆分
```
// 按业务领域：订单、库存、支付、用户、商品
// 最常用、最自然
```
按子域拆分
```
// 领域驱动设计：
// 核心域：核心竞争力（订单）
// 支撑域：辅助业务（库存）
// 通用域：通用功能（用户认证）
```
按团队/组织拆分
```
// 每个团队负责一个服务
// 康威定律：系统结构跟随组织沟通结构
```
按变更频率拆分
```
// 变更频繁的和稳定的分开
// 高频迭代的功能独立服务
```
### 服务间通信
同步 vs 异步

|对比|同步（Feign/RPC）|异步（MQ）|
|---|---|---|
|**实时性**|高|中|
|**耦合**|高（要等响应）|低（解耦）|
|**可靠性**|依赖网络|消息持久化|
|**性能**|阻塞|高|
|**适用**|强实时、需结果|解耦、削峰|
选择原则
```
// ① 需要实时结果 → 同步（Feign）
// ② 不需要立即结果 → 异步（MQ）
//    - 发短信通知、日志、统计
// ③ 削峰填谷 → 异步（MQ）
// ④ 跨服务事务 → 异步 + 最终一致

// 例子：
// 下单（同步）：扣库存 + 创建订单
// 下单后（异步）：发通知、更新统计
```
### 数据管理
数据库拆分
```
// ① 数据库隔离：
// 每个服务独立数据库（不共享）

// ② 为什么不能共享库？
// 共享库 → 强耦合 → 一个改表影响所有
// 独立库 → 各自演进 → 但无法 join

// ③ 跨服务数据怎么办？
// 冗余数据 / 聚合查询 / 最终一致
```
数据一致性
```
// 跨服务的数据操作 → 分布式事务（M10 讲过）
// 尽量：
// ① 减少跨服务事务（合理拆分）
// ② 用最终一致（MQ 异步）
// ③ 数据冗余（减少跨服务查询）
```
服务内 vs 跨服务
```
// 订单创建涉及：
// 订单库（本服务）✅ 本地事务
// 库存库（跨服务）⚠️ 分布式事务/异步

// 设计原则：
// 一个业务操作尽量在一个服务内完成（本地事务）
// 跨服务的用 MQ + 最终一致
```
### DDD 简介
```
// DDD（Domain-Driven Design）：领域驱动设计
// 以业务领域为核心来设计系统
// 先理解业务，再设计代码结构
```
核心概念
```
// ① 领域（Domain）：业务问题域（电商、支付）
// ② 子域（Sub-domain）：领域拆分（订单、库存、支付）
// ③ 限界上下文（Bounded Context）：领域边界
//    每个限界上下文 = 一个服务（或模块）
// ④ 聚合（Aggregate）：一组内聚的实体（订单 + 订单项）
// ⑤ 聚合根（Aggregate Root）：聚合的入口（订单）
// ⑥ 实体（Entity）：有 ID、可变的（订单）
// ⑦ 值对象（Value Object）：无 ID、不可变（地址）

// 一句话：
// 用"限界上下文"确定服务边界
// 用"聚合"组织服务内部结构
```
DDD与微服务的关系
```
// DDD 的限界上下文 → 微服务的拆分边界
// DDD 指导"怎么拆"（业务驱动）
// 微服务是"拆完怎么部署"（技术实现）

// 顺序：
// ① 业务分析（DDD：找限界上下文）
// ② 确定服务边界（限界上下文 → 服务）
// ③ 服务内部设计（聚合、实体）
// ④ 技术实现（Spring Cloud）

// "微服务拆分我参考 DDD：
// 先用限界上下文划清业务边界
// 每个限界上下文对应一个服务；
// 服务内部用聚合组织实体，
// 跨服务用 MQ + 最终一致保证数据。"
```
