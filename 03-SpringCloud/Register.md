## 注册中心
注册中心是什么->为什么需要->核心功能->主流实现->注册与发现流程->心跳与剔除->与redis集群对比->面试高频题
### 注册中心是什么
注册中心：微服务中服务地址的登记处。服务启动时注册自己的地址，其他服务从这里找到并调用。
```
服务A（订单）──注册──→ 注册中心（Nacos）←──注册──服务B（库存）
     │                        │                  │
     └──────发现服务B地址──────┘                  │
     └───────────────调用───────────────────────┘
```
### 为什么需要
没有注册中心的问题
```
// 微服务多实例、动态变化：
// ① 实例地址不固定（扩容/缩容/挂掉）
// ② 服务间硬编码地址 → 改一次改全量
// ③ 无法负载均衡（不知道有几个实例）
// ④ 无法健康检查（挂了不知道）

// 注册中心解决：
// ① 服务自动注册地址
// ② 消费者动态发现
// ③ 负载均衡的基础（拿到实例列表）
// ④ 健康检查 + 剔除故障实例
```
### 核心功能
| 功能       | 说明            |
| -------- | ------------- |
| **服务注册** | 服务启动时上报地址     |
| **服务发现** | 消费者获取服务实例列表   |
| **健康检查** | 心跳检测 + 剔除故障实例 |
服务注册
```
服务启动
    ↓
发送注册请求（服务名 + IP + 端口）
    ↓
注册中心登记（服务名 → 实例列表）
    ↓
定时发送心跳（续约）
```
服务发现
```
消费者调用服务
    ↓
向注册中心查询（服务名）
    ↓
拿到实例列表 [192.168.1.1:8080, 192.168.1.2:8080]
    ↓
负载均衡选一个实例
    ↓
发起调用
```
### 主流实现
| 注册中心          | 语言   | 特点              | 现状            |
| ------------- | ---- | --------------- | ------------- |
| **Nacos**     | Java | 功能全（注册+配置）、阿里   | ✅ 国内主流        |
| **Eureka**    | Java | 经典、Netflix      | ⚠️ 停更（2.x 闭源） |
| **Consul**    | Go   | HashiCorp、健康检查好 | 可用            |
| **ZooKeeper** | Java | 分布式协调、CP        | 老牌但复杂         |
| **etcd**      | Go   | K8s 生态          | 底层存储          |
```
// 国内生产主流：Nacos
// ① 注册中心 + 配置中心二合一
// ② 支持 AP（注册）和 CP（配置）两种模式
// ③ 控制台好用
// ④ 阿里生态完善（Dubbo 也兼容）
```
| 对比       | Nacos     | Eureka |
| -------- | --------- | ------ |
| **一致性**  | AP（可切 CP） | AP     |
| **配置中心** | ✅ 内置      | ❌      |
| **健康检查** | 心跳 + 主动探测 | 心跳     |
| **维护**   | ✅ 活跃      | ❌ 停更   |
| **推荐**   | ✅ 主流      | 老项目    |
### 注册和发现流程
Nacos客户端流程
```
// 服务提供者（注册）：
// ① 启动时：NacosServiceRegistry.register()
//    发送实例信息（ip、port、服务名）
// ② 定时心跳：BeatReactor 每 5 秒发心跳
// ③ 优雅关闭：deregister()

// 服务消费者（发现）：
// ① 启动时：获取服务列表（全量）
// ② 定时刷新：每 10 秒拉取（或 UDP 推送）
// ③ 本地缓存：容灾（注册中心挂了也能用缓存）
```
关键概念
```
// ① 服务名（serviceName）：逻辑分组
// ② 实例（instance）：具体地址（ip:port）
// ③ 命名空间/分组：隔离环境（dev/prod）
// ④ 权重：负载均衡的权重
// ⑤ 临时/持久实例：临时（心跳删）vs 持久（主动删）
```
### 心跳与剔除
心跳机制
```
// ① 服务每 5 秒发一次心跳（beat）
// ② 注册中心 15 秒没收到 → 标记"不健康"
// ③ 30 秒没收到 → 剔除实例
// （Nacos 参数：health-check 间隔可配）

// 参数：
// 服务端：nacos.naming.heart-beat-interval
// 客户端：spring.cloud.nacos.discovery.heart-beat-interval
```
自我保护
```
// 类似 Eureka 的自我保护：
// 短时间内大量实例掉线（网络分区）
// 注册中心进入自我保护 → 不剔除（防止误删）

// 原因：
// 网络分区时，服务其实活着，只是心跳过不去
// 如果剔除 → 消费者找不到服务 → 雪崩

// 权衡：宁可保留可能不健康的实例，也不全剔除
```
### 与redis Cluster对比
| 对比       | 注册中心（Nacos） | Redis Cluster |
| -------- | ----------- | ------------- |
| **作用**   | 服务发现        | 数据分片          |
| **存什么**  | 服务地址        | 业务数据          |
| **一致性**  | AP（注册）      | 各节点数据分片       |
| **健康检查** | 心跳          | Gossip        |
```
// 两者不同用途：
// 注册中心：管理"谁在哪"
// Redis Cluster：管理"数据在哪"
// 但都用"心跳 + 多数派"类似的原理
```
